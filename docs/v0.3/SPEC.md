Use `node:worker_threads` `new Worker(SOURCE, { eval: true, workerData })` where SOURCE is a self-contained JS string (no imports from our bundle; electron-vite/vitest must not need a separate entry). Tests: ReDoS pattern `^(a+)+$` over a 40-char line returns the timeout error within ~timeout (use a short timeout in the test), file path works, symlinks ignored.
6. exec (new exec.ts; tools.ts keeps calling it): `spawn(command, { cwd, shell: true, stdio: ['ignore','pipe','pipe'], windowsHide: true, detached: process.platform !== 'win32' })`. Timeout default 120 s. On timeout or AbortSignal: kill the whole process tree (POSIX: `process.kill(-child.pid, 'SIGKILL')`, catching ESRCH; Windows: `spawn('taskkill', ['/pid', String(pid), '/T', '/F'])`). Result text ends with `[exit N]`, `[timed out after 120 s]` or `[stopped]`. Output cap as today (MAX_OUT). Docker sandbox: when `sandbox.kind === 'docker'`, run `docker run --rm --name aioffice-<random> -v <root>:/workspace -w /workspace [--network none when !sandbox.network] [--user uid:gid on POSIX] <image> sh -lc <command>` with `shell: false`, timeout 600 s, and on timeout/abort also `docker kill <name>`. Test exec: timeout kills a grandchild (`sh -c 'sleep 30 & sleep 30'` style, assert it returns quickly and the grandchild pid is gone), abort works, stdin is closed (`cat` returns immediately).

Classify addresses: loopback (127/8, ::1), private (10/8, 172.16/12, 192.168/16, fc00::/7, 100.64/10 CGNAT), link-local (169.254/16, fe80::/10), unspecified/multicast/broadcast/reserved (0/8, 224/4, 240/4, ::), IPv4-mapped IPv6 handled. Timeout 20 s, AbortSignal. Content-type handling and htmlToText as today; keep `clip(..., 100_000)`. Export `classifyAddress(ip)` and test it thoroughly (incl. `::ffff:127.0.0.1`, `0.0.0.0`, `169.254.169.254`, `fd00::1`, public IPs). Test the fetch against a local http server: blocked without approval, allowed with approval, redirect to a blocked address rejected, size cap.

## W4 — orchestrator (file: src/main/office.ts; tests: office.test.ts, office.failures.test.ts, new office.guards.test.ts). Depends on W1–W3 being merged.

OfficeDeps additions: `stream?(agentId: string, text: string | null): void` (live reply, not persisted), `allow?(rule: string): void` (persist an allow-list entry).
Office public API: `runId`, `isRunning`, `requests` (getter), `spentUsd` (getter), `start(goal)`, `post(text, to?)`, `stop(reason?, extra?)`, `retry(agentId, model?)`, `answer(approvalId, ok, always?)`, `answerPlan(planId, approved, feedback?)`, `configure(p: Project)`.
1. Abort: one AbortController per running period; `stop()` aborts it (in-flight model requests, commands, fetches, MCP calls via Promise.race) and a fresh controller is created when the run resumes. Aborted requests are never retried and never charged (no usage).
2. Request cap: count every completed model request; when `limits.maxRequests > 0` and the count reaches it → stop with reason 'limit' (run event carries `requests`). `limits` = `project.limits ?? DEFAULT_LIMITS`.
3. Chatter guard: per unordered pair of members, count consecutive messages between them sent during wake-ups in which the sender did no other tool call (anything but message/remember counts as work; an automatic forward of the final reply counts as a message). Real work by a member resets every pair involving that member; any owner message resets all. When a pair reaches `limits.maxChatter` (> 0) → stop with reason 'loop' and `agents: [nameA, nameB]`. Test with the ping-pong scenario (must stop at exactly the threshold) and a legitimate manager/report review cycle with file reads (must not stop).
4. Budget: `post()` throws `Error('E_BUDGET_SPENT|<budget>')` when budgetUsd > 0 and spent ≥ budget (no new paid request). `configure(p)` updates budget/limits/approval/allowCommands/planFirst/sandbox of the live office (members/models are not changed mid-run). Raising the budget then posting continues the run.
5. report_to_user and stop share one cleanup: pending approvals resolved false (and `approval_done` emitted for each with approved false), pending plan cleared, blocked members unblocked (`unblocked` events), inboxes cleared, live deltas cleared (`stream(agentId, null)`).
6. MCP results are clipped to 20 000 characters (same marker as tools' clip).
7. Context: client-side "simple compaction". Track each member's last prompt size (`usage.in + cacheRead + cacheWrite`). When it is ≥ `limits.compactAt` (> 0), at the next step: send the pending tool results (if any) together with the prompt "Your conversation is getting long and will be restarted. Write a complete summary of your work so far: the task and who gave it, decisions, files you created or changed, what is verified, open problems and the exact next steps. Do not call tools." on the same chat; charge it; then discard the chat and continue on a fresh chat (same model) whose first input is `Summary of your work so far (your earlier conversation was compacted):\n\n<summary>` followed by the pending input, if any. Emit `{type:'compact', agentId, tokens}`. If the summary reply is empty, use the work log (existing `handoff` text). A provider 'context' error first triggers one log-based restart on the same model (reuse the handoff mechanism, emit `compact`), and only a second context error goes to the backup/blocked path. Tests.
8. Plan mode (`project.planFirst`): the CEO gets the `propose_plan` tool. Until a plan is approved: the CEO's `message` to anyone but the owner fails with "Propose your plan with propose_plan and wait for the owner's approval first", and the CEO's write_file/edit_file/run_command/MCP calls fail the same way (read tools allowed). propose_plan emits `{type:'plan', id, agentId, text}` and returns "Plan sent to the owner. End your turn now and wait for their answer." A second propose_plan while one is pending replaces it (emit plan_done approved:false for the old one). When the office goes idle with a pending plan the run event reason is 'plan'. `answerPlan(id, true)` → plan_done approved, then posts "[From the owner] Plan approved. Go ahead." to the CEO; `answerPlan(id, false, feedback)` → plan_done with feedback, posts "[From the owner] The plan needs changes: <feedback>". Once approved, the run stays approved (a new run starts unapproved). Without planFirst nothing changes and propose_plan is not offered.
9. Approvals: `approve(kind, command)` checks `allowCommands` first: commands match an entry when equal or starting with entry + ' ' and the command has no shell control characters (`; & | \` $ < > ( ) { } \n \r`); entries for MCP are `mcp:<label>`, for fetch `fetch:<host>`. `answer(id, ok, always)`: when ok && always, derive the rule (command: the full normalized command, only if it has no control characters — otherwise ignore `always`; mcp: `mcp:<label>`; fetch: `fetch:<host>`), add it to the live allow list and call `deps.allow(rule)`. `answer` for an unknown/already-answered id does nothing (today it emits approval_done anyway). The approval event carries `files`: workspace-relative paths written by the team since the last approved command (from runTool's `changed`), and `sandbox: true` when the office sandbox is docker. The list resets when a command is approved. Fetch approvals: ctx.approveFetch → approval kind 'fetch' with command = the URL.
10. Tool events: include `detail` = first 2000 chars of the result content (for message/report_to_user/propose_plan omit) and `diff` from runTool (write/edit), clipped to 8000 chars.
11. Live replies: pass `onText` to `step`; forward to `deps.stream(agentId, snapshot)`; after each step call `deps.stream(agentId, null)`.
12. Per-member options: `openChat(..., { effort: agent.effort, maxTokens: agent.maxTokens })`; skills: when `agent.skills` is set, the member only sees (system prompt + use_skill/read_skill_file) the enabled skills whose name is in the list; tools for skills only when that filtered list is non-empty.
13. Sandbox: pass `sandbox` (project.sandbox ?? DEFAULT_SANDBOX) and the abort signal to runTool. When a run_command result starts with `E_NO_DOCKER:` also emit a system message `E_NO_DOCKER` once per run.
14. Keep all existing behaviour and tests (delegation, retries with retry-after, backup switching, blocking/retry, budget stop, only CEO reports, continue a finished run). `answer` resolving after stop must not throw.
